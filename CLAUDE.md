# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository identity

This is a fork of **ModelScope DiffSynth-Studio** (`diffsynth` package, v2.x — see [pyproject.toml](pyproject.toml)). The directory is named `ttt-imagine-diffsynth` because it is vendored alongside the `ttt-imagine` (VideoTuna) project. The bulk of the code is upstream DiffSynth-Studio — treat it as a Diffusion model engine for inference and training of FLUX, Wan, Qwen-Image, Z-Image, LTX, HiDream, ACE-Step, Anima, MOVA, etc.

**Local addition — End-to-End Test-Time Training (E2E-TTT):** ported from the reference in the sibling `ttt-imagine` repo (`e2e_ttt_video/`) into DiffSynth-native form for `Wan2.1-T2V-1.3B` and `Wan2.2-TI2V-5B`. See the E2E-TTT section below.

Origin: `git@github.com:MarcellusZhao/ttt-imagine-diffsynth.git`. Upstream docs: https://diffsynth-studio-doc.readthedocs.io/en/latest/

## Running things

Every model family has its own folder under `examples/<family>/` with the same four-part structure:
- `model_inference/<ModelName>.py` — standalone, single-GPU inference scripts. Run with `python examples/<family>/model_inference/<ModelName>.py`. (The IDE-open file [examples/wanvideo/model_inference/Wan2.1-T2V-1.3B.py](examples/wanvideo/model_inference/Wan2.1-T2V-1.3B.py) is the canonical minimal Wan T2V example.)
- `model_inference_low_vram/<ModelName>.py` — same model with VRAM management / offload enabled.
- `model_training/train.py` — the training entrypoint for that family (one file per family, dispatched via argparse).
- `model_training/{full,lora}/<ModelName>.sh` — shell launchers that call `accelerate launch examples/<family>/model_training/train.py …` with the right flags and `modelscope download …` for the example dataset.

Pick the existing `.sh` for the variant you want and adapt; do **not** invent new argparse flags without checking [diffsynth/diffusion/parsers.py](diffsynth/diffusion/parsers.py) — the parser composition (`add_general_config`, `add_video_size_config`, etc.) is the source of truth for available flags.

Models are downloaded from ModelScope by default. Outside China set `os.environ["MODELSCOPE_DOMAIN"] = "www.modelscope.ai"`, or switch source with `DIFFSYNTH_DOWNLOAD_SOURCE` (see [docs/en/Pipeline_Usage/Environment_Variables.md](docs/en/Pipeline_Usage/Environment_Variables.md)).

## Architecture: the three layers

The repo is organized around **one pattern repeated per model family**. Understanding the layers is the fastest way to navigate:

### 1. `diffsynth/models/` — pure `nn.Module`s

One file per architecture component (DiT, VAE, text encoder, image encoder, controlnet, adapter, …). File naming is `<family>_<component>.py` (e.g. `wan_video_dit.py`, `wan_video_vae.py`, `flux_text_encoder_t5.py`). No pipeline logic here.

Loading is registry-driven: [diffsynth/configs/model_configs.py](diffsynth/configs/model_configs.py) maps a `model_hash` (hash of weight file keys) → `model_name` → `model_class` (+ optional `state_dict_converter` under [diffsynth/utils/state_dict_converters/](diffsynth/utils/state_dict_converters/)). `ModelConfig(model_id=..., origin_file_pattern=...)` resolves to a snapshot download + hash lookup. To add a new model architecture, add a class under `models/`, register the hash in `configs/model_configs.py`, and (if weights need remapping) write a converter.

### 2. `diffsynth/pipelines/<family>.py` — `BasePipeline` + `PipelineUnit` sequences

Each pipeline subclasses `BasePipeline` ([diffsynth/diffusion/base_pipeline.py](diffsynth/diffusion/base_pipeline.py)) and exposes `from_pretrained(model_configs=[...], ...)` and `__call__(**inputs)`. The pipeline's behavior is **a list of `PipelineUnit`s** stored in `self.units` (see e.g. `WanVideoPipeline.units` in [diffsynth/pipelines/wan_video.py:55](diffsynth/pipelines/wan_video.py#L55)). Each unit declares `input_params` / `output_params` and a `process()` method; the runner threads a kwargs dict through them. This is also how the training module reuses inference logic — `WanTrainingModule.forward` in [examples/wanvideo/model_training/train.py](examples/wanvideo/model_training/train.py) iterates `self.pipe.units` and calls the loss only at the end.

When adding a new conditioning modality / control / adapter, the right move is almost always **a new `PipelineUnit` inserted into `self.units`**, not new branches inside `__call__`.

### 3. `diffsynth/diffusion/` — training harness

- [training_module.py](diffsynth/diffusion/training_module.py) — `DiffusionTrainingModule` base class. Handles model loading via `parse_model_configs`, LoRA injection (`add_lora_to_model`, `auto_detect_lora_target_modules`), fp8/offload model selection, gradient checkpointing toggles, checkpoint resume, and `split_pipeline_units` for split (data-process / train) tasks.
- [runner.py](diffsynth/diffusion/runner.py) — `launch_training_task` (the standard accelerate loop) and `launch_data_process_task` (precompute embeddings/latents to disk). Both consume the same `DiffusionTrainingModule`. Task strings (`sft`, `sft:data_process`, `sft:train`, `direct_distill`, …) are dispatched in each family's `train.py`.
- [loss.py](diffsynth/diffusion/loss.py) — `FlowMatchSFTLoss`, `DirectDistillLoss`, etc.
- [parsers.py](diffsynth/diffusion/parsers.py) — composable argparse fragments. `add_general_config(parser)` is the standard bundle used by every family's `train.py`.
- [flow_match.py](diffsynth/diffusion/flow_match.py) — `FlowMatchScheduler`.

Per-family training scripts ([examples/<family>/model_training/train.py](examples/wanvideo/model_training/train.py)) subclass `DiffusionTrainingModule`, override `get_pipeline_inputs(data)` to map dataset rows → pipeline kwargs, and wire `task → loss` in `self.task_to_loss`.

## VRAM / offload model

Two distinct mechanisms — don't confuse them:

- **Inference VRAM management** ([diffsynth/core/vram/](diffsynth/core/vram/), [diffsynth/configs/vram_management_module_maps.py](diffsynth/configs/vram_management_module_maps.py)) — per-`ModelConfig` `offload_device`/`onload_device`/`offload_dtype`/`onload_dtype` fields move weights between CPU↔GPU and dtype (fp8/bf16) **layer-by-layer**. Supports disk offload via `load_model_with_disk_offload`. Configured at `from_pretrained` time.
- **Training CPU offload** ([diffsynth/core/offload_training/](diffsynth/core/offload_training/), `OffloadTrainingManager`) — enabled by `--enable_model_cpu_offload` on training scripts. Streams weights layer-by-layer during forward/backward so consumer GPUs can LoRA-train 14B models. Single-GPU only. `--enable_optimizer_cpu_offload` and `--cpu_offload_split_threshold` are sub-knobs of this.

`fp8_models` and `offload_models` argparse args take comma-separated component names (`dit,text_encoder,…`) — they apply to frozen/non-trainable models only, gradient-carrying paths must stay in bf16.

## Data pipeline

[diffsynth/core/data/unified_dataset.py](diffsynth/core/data/unified_dataset.py) — `UnifiedDataset` reads `metadata.csv` (or json) under a base path, applies a chain of **operators** ([diffsynth/core/data/operators.py](diffsynth/core/data/operators.py): `LoadVideo`, `LoadAudio`, `ImageCropAndResize`, `ToAbsolutePath`, …) composed with the `>>` operator. `--data_file_keys` (default `"image,video"`) declares which columns are file paths. Custom columns get custom operators via `special_operator_map` (see Wan's `train.py` for the `animate_face_video` / `input_audio` / `wantodance_music_path` examples).

`UnifiedDataset.default_video_operator(...)` is the standard video pipeline (handles `--height`, `--width`, `--max_pixels`, `--num_frames`, division factors). Frame/time division factors are model-specific (Wan uses 16/16/4 with remainder 1; WanToDance global uses 1/1).

## Conventions worth knowing

- **`remove_prefix_in_ckpt`** — saved LoRA / full checkpoints strip a prefix like `pipe.dit.` so they can be reloaded as standalone weights. Match the prefix the upstream model expects.
- **`lora_base_model` + `lora_target_modules`** — LoRA is added to one named submodule of the pipe (e.g. `dit`) with module name patterns (e.g. `q,k,v,o,ffn.0,ffn.2`). `auto_detect_lora_target_modules` handles cases where the right targets aren't obvious.
- **Split training (`task=sft:data_process` → `task=sft:train`)** — for very large models, first run `data_process` to dump text/VAE embeddings to disk, then run `train` with the cached embeddings to avoid re-encoding each step.
- **Diffusion Templates** ([diffsynth/diffusion/template.py](diffsynth/diffusion/template.py)) — plugin framework loaded from a directory containing a `model.py`. Used by image-to-LoRA models and other custom controllable-generation plugins.
- **NPU support** — [diffsynth/core/device/npu_compatible_device.py](diffsynth/core/device/npu_compatible_device.py) + [diffsynth/core/npu_patch/](diffsynth/core/npu_patch/) wrap device selection. Use `get_device_type()` instead of hardcoding `"cuda"` when adding new pipelines.
- **Sequence parallel** — `enable_usp()` on pipelines swaps attention/forward methods via xfuser ([diffsynth/utils/xfuser/](diffsynth/utils/xfuser/)). See [examples/wanvideo/acceleration/unified_sequence_parallel.py](examples/wanvideo/acceleration/unified_sequence_parallel.py).

## End-to-End Test-Time Training (E2E-TTT)

A DiffSynth-native port of the `e2e_ttt_video/` algorithm from the sibling `ttt-imagine` repo. Long videos are generated chunk-by-chunk; the model adapts to its own preceding chunks via a LoRA "memory scratchpad", meta-trained MAML-style so a few inner-loop steps generalize to the *next* chunk.

- **Core module** — [diffsynth/diffusion/e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py): config dataclasses (`InnerLoopConfig`, `ChunkingConfig`, `InferenceConfig`), differentiable inner-loop optimizers (`DifferentiableSGD/AdamW/Muon/MuonClip`, `MetaLearnedLRSchedule`), LoRA-state helpers, the rectified-flow loss (reuses DiffSynth's `FlowMatchScheduler` + `pipe.model_fn`), `run_meta_inner_loop` (the memorize→predict dispatcher for MAML/FOMAML/Reptile — see `--e2e_algorithm` below; Reptile routes to `_run_reptile_inner_loop`), the first-order test-time `ttt_update_inplace`, and `WanE2ETTTSequentialGenerator`.
- **Meta-training** — [examples/wanvideo/model_training/train_e2e_ttt.py](examples/wanvideo/model_training/train_e2e_ttt.py) subclasses `WanTrainingModule`; its `forward` splits each video into chunks and returns a single scalar the stock `launch_training_task` back-propagates (no W0-restore hook needed: `write_back=False` keeps LoRA leaves at φ₀ so the outer AdamW updates φ₀ directly). The `--e2e_algorithm` flag selects the meta-learning variant — all three return a scalar whose `.backward()` deposits the right φ₀ gradient, so the outer loop is identical across them:
  - `maml` (default) — exact second-order MAML; scalar = mean next-chunk **predict** loss (`create_graph=True`).
  - `fomaml` — first-order MAML; same predict-loss scalar, Hessian dropped (`create_graph=False`); grad reaches φ₀ only via the clone→φ₀ identity path. `--e2e_first_order` is a back-compat alias.
  - `reptile` — plain SGD adaptation on the memorize chunks, then move φ₀ toward the adapted weights; scalar = **surrogate** `Σₙ⟨φ₀ⁿ, (φ₀ⁿ−φ_Kⁿ).detach()⟩` whose grad equals the Reptile pseudo-gradient `φ₀−φ_K` (no predict term, no second-order graph). Reptile has no meta-objective, so logged `train/meta_loss` is `0` (`num_pred_pairs`=0); watch `train/memorize_loss` for the fit instead. **Multi-GPU caveat:** the Reptile surrogate does not route through the DDP-wrapped DiT forward, so `find_unused_parameters` / manual grad all-reduce may be needed for >1 GPU; single-GPU is unaffected.
  - Launchers (each takes a YAML from [model_training/configs/](examples/wanvideo/model_training/configs/) as its first arg): [Wan2.1-T2V-1.3B-e2e-ttt-maml.sh](examples/wanvideo/model_training/lora/Wan2.1-T2V-1.3B-e2e-ttt-maml.sh), [-fomaml.sh](examples/wanvideo/model_training/lora/Wan2.1-T2V-1.3B-e2e-ttt-fomaml.sh), [-reptile.sh](examples/wanvideo/model_training/lora/Wan2.1-T2V-1.3B-e2e-ttt-reptile.sh); the same trio for Wan2.1-Fun-V1.1-1.3B-InP; [Wan2.1-T2V-14B-e2e-ttt-fomaml.sh](examples/wanvideo/model_training/lora/Wan2.1-T2V-14B-e2e-ttt-fomaml.sh); [Wan2.2-TI2V-5B-e2e-ttt-fomaml.sh](examples/wanvideo/model_training/lora/Wan2.2-TI2V-5B-e2e-ttt-fomaml.sh).
- **Sequential inference** — single-prompt scripts: [Wan2.1-T2V-1.3B-e2e-ttt-custom.py](examples/wanvideo/model_inference/Wan2.1-T2V-1.3B-e2e-ttt-custom.py), [custom-prompts/Wan2.2-TI2V-5B-e2e-ttt-custom.py](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-e2e-ttt-custom.py). VBench suite sampling: [Wan2.1-T2V-1.3B-e2e-ttt-vbench.py](examples/wanvideo/model_inference/Wan2.1-T2V-1.3B-e2e-ttt-vbench.py) (per-algorithm `.sh` wrappers alongside), [vbench/Wan2.2-TI2V-5B-e2e-ttt-vbench.py](examples/wanvideo/model_inference/vbench/Wan2.2-TI2V-5B-e2e-ttt-vbench.py); YAML configs under [model_inference/configs/](examples/wanvideo/model_inference/configs/). Pass `--lora <ckpt>` to load a meta-trained φ₀ (a missing path falls back to a zero-init identity adapter). The TI2V-5B scripts have three anchoring switches, **all on by default**, each turned off by a single `--no_*` flag: `condition_on_last_frame` (anchor each chunk on the previous chunk's last frame, matching training), `condition_on_sink_frame` (also pin the whole video's first frame as a fixed second anchor — mirrors training's `--e2e_condition_on_sink_frame`, likewise default-on; pass `--no_condition_on_sink_frame` for a φ₀ meta-trained without it), and `drop_boundary_frame`. The sink requires last-frame conditioning; `--no_condition_on_last_frame` normalizes the sink off with a NOTE rather than erroring. With the sink on, two leading latent frames are pinned per follow-up chunk, so `drop_boundary_frame` trims 5 decoded frames instead of 1 — see `num_pinned_pixel_frames` in [e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py).
- **No-adaptation baselines** (same chunk loop, base weights, no LoRA and no TTT — the arms an E2E-TTT number is read against): [custom-prompts/Wan2.2-TI2V-5B-chunk-by-chunk-custom.py](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-chunk-by-chunk-custom.py) is the plain one (single last frame via `input_image`, `--no_condition_on_last_chunk` for independent chunks), and [custom-prompts/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-custom.py](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-custom.py) reproduces the **full E2E-TTT anchoring** — wide k-frame block (`--num_anchor_latent_frames`, default **3** here, vs `1` on the TTT scripts) plus the first-frame sink, same `--no_*` flags and same sink normalization — so the LoRA scratchpad is the only difference from a TTT run. It imports `anchor_overlap_pixel_frames` / `num_clean_latents` / `num_pinned_pixel_frames` from [e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py) rather than duplicating the arithmetic, and raises upfront if `--frames_per_chunk` is too short for the anchor window. Commented invocations for both live in [Wan2.2-TI2V-5B-custom-prompt-eval.sh](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-custom-prompt-eval.sh), which by convention keeps exactly one line uncommented per run. Both have VBench-suite drivers under [vbench/](examples/wanvideo/model_inference/vbench/) with the same `--config` / sharding / `<prompt>-<index>.mp4` protocol as the TTT one: [vbench/Wan2.2-TI2V-5B-chunk-by-chunk-vbench.py](examples/wanvideo/model_inference/vbench/Wan2.2-TI2V-5B-chunk-by-chunk-vbench.py) (plain) and [vbench/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.py](examples/wanvideo/model_inference/vbench/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.py) (full anchoring; config [Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.yaml](examples/wanvideo/model_inference/configs/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.yaml) mirrors the k3-720p TTT arm's geometry at `fpc=49` / 24 chunks so total length matches — VBench metrics are length-sensitive, so keep `num_chunks`/`frames_per_chunk`/k/resolution equal across arms). All three drivers derive chunk seeds identically (`base_seed + index*num_chunks + k`), so arms share seeds clip for clip.
- **Wide local anchor (`k`)** — `--e2e_num_anchor_latent_frames` (training) / `--num_anchor_latent_frames` (inference), default `1`. A *single* anchor latent is motion-unidentifiable — no velocity can be read off one frame — so at k=1 the only channel carrying motion **direction** across a chunk boundary is the LoRA scratchpad, whose memorize objective is unconditioned flow matching and therefore dominated by appearance. That is the known cause of next chunks that reverse the preceding motion. k>1 pins a contiguous *block* of the previous chunk's tail, putting velocity directly in the conditioning. The two values must match between the φ₀ checkpoint and the sampling script — k sets both how many leading latents are pinned and how many decoded frames each chunk hands forward. Mechanics: `anchor_overlap_pixel_frames(k, sink)` is both the meta-training chunk overlap and the inference handoff window, so anchor latents are byte-identical across train/test; with a sink the block is displaced to latent positions `1..k` (sliced as `x0[:, :, 1:1+k]`) and the window carries one extra leading frame purely as VAE causal context, whose latent the sink overwrites — hence `4k+1` (k=3 → 13 pixel frames of overlap, 12 anchored). The anchor block **must** come from one contiguous VAE encode: Wan's causal VAE gives latent 0 one pixel frame and later latents four, so stacking standalone single-frame encodes at positions >0 yields wrong statistics (`WanVideoUnit_ImageEmbedderFused` takes an `anchor_frames` list and encodes it in one pass). The recycled anchor y-error is likewise harvested and injected as one coherent k-frame block (the predict chunk's last k latents) — independent per-frame draws would inject temporally incoherent noise into the exact cue k exists to provide. **k=1 is a deliberate legacy special case** (anchor at `x0[:, :, 0:1]`, sink prepended, 1-frame overlap) so pre-existing φ₀ checkpoints still reproduce. Cost: pinned frames are given context, not supervised content — at `frames_per_chunk=41` a k=3+sink block pins 4 of 11 latents (7 supervised vs 9 at k=1), so raise `e2e_frames_per_chunk` rather than accepting a weaker meta signal. Watch `train/num_anchor_latent_frames` and `train/anchor_overlap_frames`. Ready-made pairs: [fomaml-k3-720p.yaml](examples/wanvideo/model_training/configs/Wan2.2-TI2V-5B-e2e-ttt-fomaml-k3-720p.yaml) + [k3-720p-vbench.yaml](examples/wanvideo/model_inference/configs/Wan2.2-TI2V-5B-e2e-ttt-k3-720p-vbench.yaml) (controlled arm: 720p training at `fpc=49`, which restores the k=1 baseline's 9 supervised latents *and* its 36 new frames/chunk, so k is the only variable that moves) and [fomaml-k3-480p.yaml](examples/wanvideo/model_training/configs/Wan2.2-TI2V-5B-e2e-ttt-fomaml-k3-480p.yaml) + [k3-480p-vbench.yaml](examples/wanvideo/model_inference/configs/Wan2.2-TI2V-5B-e2e-ttt-k3-480p-vbench.yaml) (train fpc=49, infer fpc=93 @ 480p for 80 new frames/chunk).
- **Frame sampling (`--fix_frame_rate` / `--frame_rate`)** — `--fix_frame_rate` (default **off**) resamples every clip's time axis to `--frame_rate` (default `None`, and **only read when `--fix_frame_rate` is set**); off, clips are read as their native frame sequence and `--frame_rate` is inert. The pair is enforced: `--fix_frame_rate` without an explicit `--frame_rate` raises in [train_e2e_ttt.py](examples/wanvideo/model_training/train_e2e_ttt.py) rather than inheriting a default. Getting the target fps *wrong* is worse than leaving the switch off — resampling **down** just drops frames, but resampling **up** duplicates them, making consecutive outputs identical and the inter-frame motion zero, which poisons exactly the velocity cue a k>1 anchor block exists to carry (16fps clips at `--frame_rate 24` duplicate every third frame). `LoadVideo` warns per clip when the source fps is below the target; such clips should be *filtered out*, not resampled up. The five `Wan2.2-TI2V-5B-*` configs set `fix_frame_rate: true` / `frame_rate: 16`: the clips are already 16fps (resampled offline — `rsfps16` in `output_path`, verified byte-identical: same frames, ≤4 fewer at the tail on some clips), but that uniformity was an **unenforced precondition living only in a preprocessing step**, and E2E-TTT is unusually sensitive to it. It is also strictly cheaper — the frame count then comes from the container's `duration` instead of `reader.count_frames()`, which shells out to a full `ffmpeg -c copy -f null -` demux pass (0.7–2.5 s on a 300-frame 540p clip). [operators.py](diffsynth/core/data/operators.py) was reworked to pay for that pass only when unavoidable: `count_frames()` per clip went 2 → 1 with `fix_frame_rate` off and 2 → **0** with it on, and `LoadVideo` now guards `get_data` with an `IndexError` catch (a `duration` that over-states the real length truncates and re-snaps to the division factor instead of crashing). `map_single_frame_id`'s `total_raw_frames` is now optional for the same reason.
- **Throughput: length-grouped batching + prefetch** — under DDP every rank blocks at the gradient all-reduce, so a step costs as much as its **longest** clip; chunk counts span 3–23 (median 6) on `ultravideo_long_filtered_all_16k`, and a random window of 8 almost always contains an outlier (`Σ_steps max(n)` = 1.92× the balanced floor). `--length_grouped_batching` (opt-in) replaces the default global shuffle with `LengthGroupedSampler` in [train_e2e_ttt.py](examples/wanvideo/model_training/train_e2e_ttt.py), passed through the new `sampler=` parameter of `launch_training_task` ([runner.py](diffsynth/diffusion/runner.py)). It works purely by *reordering* because accelerate shards a `batch_size=1` loader round-robin (`BatchSamplerShard._iter_with_no_split`: sampler position `i` → rank `i % num_processes`) without reordering, so the clips co-resident in one step are exactly the contiguous window `[g·G, (g+1)·G)` where `G = num_processes * gradient_accumulation_steps`. Scheme (HF's "sortish"): global shuffle → cut into megabatches of `G * --length_group_megabatch_mult` → sort each by length → cut into `G`-sized groups → **shuffle the groups**. That last shuffle matters: without it clip length correlates with training *time* and the LR warmup/cosine and the `ErrorRecycler` warmup each see a biased slice. Measured at 8 GPUs: 1.92× → 1.03×, 76% of steps perfectly uniform, ~1.87× predicted speedup. `--length_column` (default `num_frames`, generated by [add_length_column.py](datasets/ultravideo_long/add_length_column.py)) is a **scheduling hint only** — `LoadVideo` still measures the real length, so a stale value costs balance and can never change what is trained. Note `--length_group_megabatch_mult` runs the *opposite* way to its help string: `1` degenerates to a plain random shuffle (the sort window equals one group), and only `≥ len(dataset)/G` approaches a global sort; the default `50` (400-clip window) captures ~98% of the benefit while keeping sampling randomness. The startup `imbalance_report` line models step cost as `max` over the whole window, which is exact at `gradient_accumulation_steps=1` and over-states the speedup above it. Orthogonal second lever: `--dataset_num_workers` defaults to **0**, i.e. video decode (5–11 s/clip) runs synchronously on the training loop's critical path; the TI2V-5B configs set `2`, which drops the measured per-step stall from ~6.5 s to ~1.0 s (the residue is IPC of the decoded PIL frames). Cost is `workers × prefetch_factor(2) ×` clip size (~1.2 MB/frame at 480p, ~2.8 MB at 720p).
- **Two correctness constraints** (both handled in code): (1) second-order grads (`maml` only) require double-backward attention — `enable_double_backward_attention()` disables fused flash/sage kernels and pins math SDPA; it is called only when `--e2e_algorithm maml`, since FOMAML and Reptile each do a single backward per inner step and run fine with fused kernels; (2) the differentiable override path must run **without** activation checkpointing (non-reentrant checkpoint recomputes after the param-override context exits), enforced in `compute_flow_matching_loss`.

- [ ] Persist and restore `ErrorRecycler` state (noise/y/anchor replay buffers, warmup `iteration_count`, and counters) when resumable anti-drift post-training is needed. Current uninterrupted 3k-example runs intentionally start with fresh recycler state.

**Open design questions — "the memorize objective stores texture, not dynamics".** Both of the following attack the same root cause as the wide-anchor (`k>1`) work, but on the *inner* loss instead of the conditioning: the memorize objective is unconditioned flow matching on a chunk, so what the LoRA scratchpad actually absorbs is appearance statistics, and motion direction is only weakly represented. Both are cheap; neither has been run. (Rejected alternative, for the record: swapping the memorize loss for a **DMD**-style distribution-matching objective. It is not substitutable — DMD needs the sample to be a differentiable function of the params being updated, whereas the memorized `x0` is a detached leaf (ground truth in training, sampler output at test time), so it would require a differentiable rollout per inner step *inside* the MAML graph; and its `s_real` is the frozen teacher, so it is mode-seeking toward *teacher-plausible* video rather than toward *this chunk* — it carries no per-sample identity signal, which is exactly what the scratchpad exists to hold. Making `s_real` sample-specific degenerates back to the flow-matching residual already in use, plus a learned fake-score net of variance. DMD's real place in this project is offline few-step distillation of the base model, orthogonal to TTT, and/or a Self-Forcing-style rollout loss in the **outer/predict** term where "plausible continuation" is genuinely a distribution-level notion.)

- [ ] **Condition the memorize objective on the anchor.** Today it is deliberately unconditioned: the memorize call at [e2e_ttt.py:1449](diffsynth/diffusion/e2e_ttt.py#L1449) passes neither `condition_on_first_frame` nor `sink_frame`/`num_anchor_latent_frames`, and `ttt_update_inplace` ([e2e_ttt.py:1529](diffsynth/diffusion/e2e_ttt.py#L1529)) has no parameters for them either — so train and test are at least *symmetric* in being unconditioned. Conditioned, "memorize" would mean *continue-from-these-frames* rather than *reproduce this clip*, forcing the scratchpad to encode dynamics; the anchor block is precisely where velocity lives (same argument as `k>1`). Implementation is small because the frames are already in hand on both sides: in meta-training `chunks[k]` is overlap-chunked, so its leading `num_clean_latents(k, sink)` latents *are* the anchor; at inference `x0 = chunk_latents` is the sampler's own output for a follow-up chunk, whose leading latents are the ones the pipeline pinned. Open sub-questions: (a) chunk 0 / the first memorize step has no predecessor, so it stays unconditioned — does the inner objective then change shape between step 0 and later steps in a way the meta-learned LR schedule can absorb? (b) pinned frames are excluded from the loss, so a conditioned memorize step supervises `T' − num_clean` instead of `T'` latents — the same supervised-frame tax that made `fpc=49` the controlled setting for k=3; (c) train and test must be changed together (`ttt_update_inplace` needs the new args threaded through `WanE2ETTTSequentialGenerator`), and a φ₀ trained conditioned is not interchangeable with one trained unconditioned.
- [ ] **Bias the memorize timestep window high.** Low-σ draws are where the loss is texture-fitting; high-σ draws carry layout and motion. Training side is config-only — `--e2e_min_timestep_boundary` / `--e2e_max_timestep_boundary` already exist ([train_e2e_ttt.py:544](examples/wanvideo/model_training/train_e2e_ttt.py#L544)) and feed `InnerLoopConfig.min/max_timestep_boundary`; they are distinct from the non-`e2e_` pair, which bounds the outer/SFT loss. Caveat before running it as a pure config sweep: the **inference** scripts never set these fields (see the `InnerLoopConfig(...)` construction in [vbench/Wan2.2-TI2V-5B-e2e-ttt-vbench.py:316](examples/wanvideo/model_inference/vbench/Wan2.2-TI2V-5B-e2e-ttt-vbench.py#L316)), so test-time TTT would keep sampling `0.0–1.0` and no longer match the meta-trained inner update — a CLI flag has to be added on the sampling side for the arms to be comparable.
