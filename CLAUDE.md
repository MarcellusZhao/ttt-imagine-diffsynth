# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository identity

This is a fork of **ModelScope DiffSynth-Studio** (`diffsynth` package, v2.x — see [pyproject.toml](pyproject.toml)). The directory is named `ttt-imagine-diffsynth` because it is vendored alongside the `ttt-imagine` (VideoTuna) project. The bulk of the code is upstream DiffSynth-Studio — treat it as a Diffusion model engine for inference and training of FLUX, Wan, Qwen-Image, Z-Image, LTX, HiDream, ACE-Step, Anima, MOVA, etc.

**Local addition — End-to-End Test-Time Training (E2E-TTT):** ported from the reference in the sibling `ttt-imagine` repo (`e2e_ttt_video/`) into DiffSynth-native form for `Wan2.1-T2V-1.3B` and `Wan2.2-TI2V-5B`. See the E2E-TTT section below.

Origin: `git@github.com:MarcellusZhao/ttt-imagine-diffsynth.git`. Upstream docs: https://diffsynth-studio-doc.readthedocs.io/en/latest/

## Running things

Every model family has its own folder under `examples/<family>/` with the same four-part structure:
- `model_inference/<ModelName>.py` — standalone, single-GPU inference scripts. Run with `python examples/<family>/model_inference/<ModelName>.py`. (The IDE-open file [examples/wanvideo/model_inference/Wan2.1-T2V-1.3B.py](examples/wanvideo/model_inference/Wan2.1-T2V-1.3B.py) is the canonical minimal Wan T2V example.)
- `model_inference_low_vram/<ModelName>.py` — same model with VRAM management / offload enabled.
- `model_training/train.py` — the training entrypoint for that family (one file per family, dispatched via argparse).
- `model_training/{full,lora}/<ModelName>.sh` — shell launchers that call `accelerate launch examples/<family>/model_training/train.py …` with the right flags and `modelscope download …` for the example dataset.

Pick the existing `.sh` for the variant you want and adapt; do **not** invent new argparse flags without checking [diffsynth/diffusion/parsers.py](diffsynth/diffusion/parsers.py) — the parser composition (`add_general_config`, `add_video_size_config`, etc.) is the source of truth for available flags.

Models are downloaded from ModelScope by default. Outside China set `os.environ["MODELSCOPE_DOMAIN"] = "www.modelscope.ai"`, or switch source with `DIFFSYNTH_DOWNLOAD_SOURCE` (see [docs/en/Pipeline_Usage/Environment_Variables.md](docs/en/Pipeline_Usage/Environment_Variables.md)).

## Architecture: the three layers

The repo is organized around **one pattern repeated per model family**. Understanding the layers is the fastest way to navigate:

### 1. `diffsynth/models/` — pure `nn.Module`s

One file per architecture component (DiT, VAE, text encoder, image encoder, controlnet, adapter, …). File naming is `<family>_<component>.py` (e.g. `wan_video_dit.py`, `wan_video_vae.py`, `flux_text_encoder_t5.py`). No pipeline logic here.

Loading is registry-driven: [diffsynth/configs/model_configs.py](diffsynth/configs/model_configs.py) maps a `model_hash` (hash of weight file keys) → `model_name` → `model_class` (+ optional `state_dict_converter` under [diffsynth/utils/state_dict_converters/](diffsynth/utils/state_dict_converters/)). `ModelConfig(model_id=..., origin_file_pattern=...)` resolves to a snapshot download + hash lookup. To add a new model architecture, add a class under `models/`, register the hash in `configs/model_configs.py`, and (if weights need remapping) write a converter.

### 2. `diffsynth/pipelines/<family>.py` — `BasePipeline` + `PipelineUnit` sequences

Each pipeline subclasses `BasePipeline` ([diffsynth/diffusion/base_pipeline.py](diffsynth/diffusion/base_pipeline.py)) and exposes `from_pretrained(model_configs=[...], ...)` and `__call__(**inputs)`. The pipeline's behavior is **a list of `PipelineUnit`s** stored in `self.units` (see e.g. `WanVideoPipeline.units` in [diffsynth/pipelines/wan_video.py:55](diffsynth/pipelines/wan_video.py#L55)). Each unit declares `input_params` / `output_params` and a `process()` method; the runner threads a kwargs dict through them. This is also how the training module reuses inference logic — `WanTrainingModule.forward` in [examples/wanvideo/model_training/train.py](examples/wanvideo/model_training/train.py) iterates `self.pipe.units` and calls the loss only at the end.

When adding a new conditioning modality / control / adapter, the right move is almost always **a new `PipelineUnit` inserted into `self.units`**, not new branches inside `__call__`.

### 3. `diffsynth/diffusion/` — training harness

- [training_module.py](diffsynth/diffusion/training_module.py) — `DiffusionTrainingModule` base class. Handles model loading via `parse_model_configs`, LoRA injection (`add_lora_to_model`, `auto_detect_lora_target_modules`), fp8/offload model selection, gradient checkpointing toggles, checkpoint resume, and `split_pipeline_units` for split (data-process / train) tasks.
- [runner.py](diffsynth/diffusion/runner.py) — `launch_training_task` (the standard accelerate loop) and `launch_data_process_task` (precompute embeddings/latents to disk). Both consume the same `DiffusionTrainingModule`. Task strings (`sft`, `sft:data_process`, `sft:train`, `direct_distill`, …) are dispatched in each family's `train.py`.
- [loss.py](diffsynth/diffusion/loss.py) — `FlowMatchSFTLoss`, `DirectDistillLoss`, etc.
- [parsers.py](diffsynth/diffusion/parsers.py) — composable argparse fragments. `add_general_config(parser)` is the standard bundle used by every family's `train.py`.
- [flow_match.py](diffsynth/diffusion/flow_match.py) — `FlowMatchScheduler`.

Per-family training scripts ([examples/<family>/model_training/train.py](examples/wanvideo/model_training/train.py)) subclass `DiffusionTrainingModule`, override `get_pipeline_inputs(data)` to map dataset rows → pipeline kwargs, and wire `task → loss` in `self.task_to_loss`.

## VRAM / offload model

Two distinct mechanisms — don't confuse them:

- **Inference VRAM management** ([diffsynth/core/vram/](diffsynth/core/vram/), [diffsynth/configs/vram_management_module_maps.py](diffsynth/configs/vram_management_module_maps.py)) — per-`ModelConfig` `offload_device`/`onload_device`/`offload_dtype`/`onload_dtype` fields move weights between CPU↔GPU and dtype (fp8/bf16) **layer-by-layer**. Supports disk offload via `load_model_with_disk_offload`. Configured at `from_pretrained` time.
- **Training CPU offload** ([diffsynth/core/offload_training/](diffsynth/core/offload_training/), `OffloadTrainingManager`) — enabled by `--enable_model_cpu_offload` on training scripts. Streams weights layer-by-layer during forward/backward so consumer GPUs can LoRA-train 14B models. Single-GPU only. `--enable_optimizer_cpu_offload` and `--cpu_offload_split_threshold` are sub-knobs of this.

`fp8_models` and `offload_models` argparse args take comma-separated component names (`dit,text_encoder,…`) — they apply to frozen/non-trainable models only, gradient-carrying paths must stay in bf16.

## Data pipeline

[diffsynth/core/data/unified_dataset.py](diffsynth/core/data/unified_dataset.py) — `UnifiedDataset` reads `metadata.csv` (or json) under a base path, applies a chain of **operators** ([diffsynth/core/data/operators.py](diffsynth/core/data/operators.py): `LoadVideo`, `LoadAudio`, `ImageCropAndResize`, `ToAbsolutePath`, …) composed with the `>>` operator. `--data_file_keys` (default `"image,video"`) declares which columns are file paths. Custom columns get custom operators via `special_operator_map` (see Wan's `train.py` for the `animate_face_video` / `input_audio` / `wantodance_music_path` examples).

`UnifiedDataset.default_video_operator(...)` is the standard video pipeline (handles `--height`, `--width`, `--max_pixels`, `--num_frames`, division factors). Frame/time division factors are model-specific (Wan uses 16/16/4 with remainder 1; WanToDance global uses 1/1).

## Conventions worth knowing

- **`remove_prefix_in_ckpt`** — saved LoRA / full checkpoints strip a prefix like `pipe.dit.` so they can be reloaded as standalone weights. Match the prefix the upstream model expects.
- **`lora_base_model` + `lora_target_modules`** — LoRA is added to one named submodule of the pipe (e.g. `dit`) with module name patterns (e.g. `q,k,v,o,ffn.0,ffn.2`). `auto_detect_lora_target_modules` handles cases where the right targets aren't obvious.
- **Split training (`task=sft:data_process` → `task=sft:train`)** — for very large models, first run `data_process` to dump text/VAE embeddings to disk, then run `train` with the cached embeddings to avoid re-encoding each step.
- **Diffusion Templates** ([diffsynth/diffusion/template.py](diffsynth/diffusion/template.py)) — plugin framework loaded from a directory containing a `model.py`. Used by image-to-LoRA models and other custom controllable-generation plugins.
- **NPU support** — [diffsynth/core/device/npu_compatible_device.py](diffsynth/core/device/npu_compatible_device.py) + [diffsynth/core/npu_patch/](diffsynth/core/npu_patch/) wrap device selection. Use `get_device_type()` instead of hardcoding `"cuda"` when adding new pipelines.
- **Sequence parallel** — `enable_usp()` on pipelines swaps attention/forward methods via xfuser ([diffsynth/utils/xfuser/](diffsynth/utils/xfuser/)). See [examples/wanvideo/acceleration/unified_sequence_parallel.py](examples/wanvideo/acceleration/unified_sequence_parallel.py).

## End-to-End Test-Time Training (E2E-TTT)

A DiffSynth-native port of the `e2e_ttt_video/` algorithm from the sibling `ttt-imagine` repo. Long videos are generated chunk-by-chunk; the model adapts to its own preceding chunks via a LoRA "memory scratchpad", meta-trained MAML-style so a few inner-loop steps generalize to the *next* chunk.

- **Core module** — [diffsynth/diffusion/e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py): config dataclasses (`InnerLoopConfig`, `ChunkingConfig`, `InferenceConfig`), differentiable inner-loop optimizers (`DifferentiableSGD/AdamW/Muon/MuonClip`, `MetaLearnedLRSchedule`), LoRA-state helpers, the rectified-flow loss (reuses DiffSynth's `FlowMatchScheduler` + `pipe.model_fn`), `run_meta_inner_loop` (the memorize→predict dispatcher for MAML/FOMAML/Reptile — see `--e2e_algorithm` below; Reptile routes to `_run_reptile_inner_loop`), the first-order test-time `ttt_update_inplace` + `TestTimeInnerOptimizer`, the anchoring-route builders (`build_i2v_conditioning` + `motion_latent_frames` for the `i2v` route, `attention_anchor_latents` for the prefix route, `anchor_overlap_pixel_frames`/`num_clean_latents`/`num_pinned_pixel_frames` for the fused one), and `WanE2ETTTSequentialGenerator`.
- **Test-time inner loop must match the meta-trained one** — `ttt_update_inplace` applies the update through `TestTimeInnerOptimizer`, which routes `inner_cfg.optimizer` to the same `make_inner_optimizer` factory meta-training uses and keeps optimizer state (AdamW moments / Muon momentum) alive for one video, reset with φ₀ between videos — mirroring `run_meta_inner_loop`, where `opt` is built once per outer step. It runs on an **fp32 master copy** of the LoRA leaves because bf16's quantum at LoRA's parameter scale (~7e-5) is larger than a clipped SGD increment (~1.6e-7), so an in-place bf16 `sub_` discards most of the update and cannot accumulate what it discards. Until this was fixed the function hardcoded plain SGD and ignored `optimizer` entirely: an AdamW-meta-trained φ₀ was adapted by a rule whose realized `‖Δφ‖/‖φ‖` was **~7200× smaller** (measured, rank 128, lr 1e-4, 2 steps), so every TTT arm was effectively the anchored baseline with φ₀ frozen. The `--optimizer` CLI default is still `sgd` while every `Wan2.2-TI2V-5B-*` training config uses `adamw`, so the sampling YAML **must** set `optimizer: adamw` explicitly — all three TI2V-5B inference configs now do. Note the effective test-time step count is `ttt_steps_per_chunk × num_gradient_steps`.
- **Meta-training** — [examples/wanvideo/model_training/train_e2e_ttt.py](examples/wanvideo/model_training/train_e2e_ttt.py) subclasses `WanTrainingModule`; its `forward` splits each video into chunks and returns a single scalar the stock `launch_training_task` back-propagates (no W0-restore hook needed: `write_back=False` keeps LoRA leaves at φ₀ so the outer AdamW updates φ₀ directly). The `--e2e_algorithm` flag selects the meta-learning variant — all three return a scalar whose `.backward()` deposits the right φ₀ gradient, so the outer loop is identical across them:
  - `maml` (default) — exact second-order MAML; scalar = mean next-chunk **predict** loss (`create_graph=True`).
  - `fomaml` — first-order MAML; same predict-loss scalar, Hessian dropped (`create_graph=False`); grad reaches φ₀ only via the clone→φ₀ identity path. `--e2e_first_order` is a back-compat alias.
  - `reptile` — plain SGD adaptation on the memorize chunks, then move φ₀ toward the adapted weights; scalar = **surrogate** `Σₙ⟨φ₀ⁿ, (φ₀ⁿ−φ_Kⁿ).detach()⟩` whose grad equals the Reptile pseudo-gradient `φ₀−φ_K` (no predict term, no second-order graph). Reptile has no meta-objective, so logged `train/meta_loss` is `0` (`num_pred_pairs`=0); watch `train/memorize_loss` for the fit instead. **Multi-GPU caveat:** the Reptile surrogate does not route through the DDP-wrapped DiT forward, so `find_unused_parameters` / manual grad all-reduce may be needed for >1 GPU; single-GPU is unaffected.
  - Launchers (each takes a YAML from [model_training/configs/](examples/wanvideo/model_training/configs/) as its first arg): [Wan2.1-T2V-1.3B-e2e-ttt-maml.sh](examples/wanvideo/model_training/lora/Wan2.1-T2V-1.3B-e2e-ttt-maml.sh), [-fomaml.sh](examples/wanvideo/model_training/lora/Wan2.1-T2V-1.3B-e2e-ttt-fomaml.sh), [-reptile.sh](examples/wanvideo/model_training/lora/Wan2.1-T2V-1.3B-e2e-ttt-reptile.sh); the same trio for Wan2.1-Fun-V1.1-1.3B-InP; [Wan2.1-T2V-14B-e2e-ttt-fomaml.sh](examples/wanvideo/model_training/lora/Wan2.1-T2V-14B-e2e-ttt-fomaml.sh); [Wan2.2-TI2V-5B-e2e-ttt-fomaml.sh](examples/wanvideo/model_training/lora/Wan2.2-TI2V-5B-e2e-ttt-fomaml.sh).
- **Sequential inference** — custom-prompt scripts: [Wan2.1-T2V-1.3B-e2e-ttt-custom.py](examples/wanvideo/model_inference/Wan2.1-T2V-1.3B-e2e-ttt-custom.py), [custom-prompts/Wan2.2-TI2V-5B-e2e-ttt-custom.py](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-e2e-ttt-custom.py), [custom-prompts/Wan2.1-Fun-V1.1-1.3B-InP-e2e-ttt-custom.py](examples/wanvideo/model_inference/custom-prompts/Wan2.1-Fun-V1.1-1.3B-InP-e2e-ttt-custom.py) (the `i2v` route — its anchoring flags are `--num_motion_frames`/`--ref_pad_num`, not `--num_anchor_latent_frames`). VBench suite sampling: [Wan2.1-T2V-1.3B-e2e-ttt-vbench.py](examples/wanvideo/model_inference/Wan2.1-T2V-1.3B-e2e-ttt-vbench.py) (per-algorithm `.sh` wrappers alongside), [vbench/Wan2.2-TI2V-5B-e2e-ttt-vbench.py](examples/wanvideo/model_inference/vbench/Wan2.2-TI2V-5B-e2e-ttt-vbench.py); YAML configs under [model_inference/configs/](examples/wanvideo/model_inference/configs/). Pass `--lora <ckpt>` to load a meta-trained φ₀ (a missing path falls back to a zero-init identity adapter). The TI2V-5B scripts have three anchoring switches, **all on by default**, each turned off by a single `--no_*` flag: `condition_on_last_frame` (anchor each chunk on the previous chunk's last frame, matching training), `condition_on_sink_frame` (also pin the whole video's first frame as a fixed second anchor — mirrors training's `--e2e_condition_on_sink_frame`, likewise default-on; pass `--no_condition_on_sink_frame` for a φ₀ meta-trained without it), and `drop_boundary_frame`. The sink requires last-frame conditioning; `--no_condition_on_last_frame` normalizes the sink off with a NOTE rather than erroring. A fourth default-on switch on the same three TI2V-5B scripts (the 1.3B ones do not have it and keep the library default of off), `use_gradient_checkpointing` (turned off by `--no_gradient_checkpointing`), governs the **test-time memorize backward** only: at test time `params_override is None`, so the inner loop takes the stock `pipe.model_fn(use_gradient_checkpointing=True)` path — same update, one extra forward per inner step, no relation to correctness constraint (2) below, which is about the differentiable *override* path in meta-training. It is what keeps the inner loop inside 96 GB at 720p: retaining all 30 blocks' activations for a 704×1280 chunk OOMs on an H100 at `frames_per_chunk=53` (14 latent frames → 12320 tokens) while `fpc=49` (13 → 11440) just fits, so a 720p arm silently depends on chunk length without it. With the sink on, two leading latent frames are pinned per follow-up chunk, so `drop_boundary_frame` trims 5 decoded frames instead of 1 — see `num_pinned_pixel_frames` in [e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py). **Memory probe:** [memory-test/Wan2.2-TI2V-5B-e2e-ttt-memory.py](examples/wanvideo/model_inference/memory-test/Wan2.2-TI2V-5B-e2e-ttt-memory.py) drives the same loop from a *per-chunk prompt schedule* (`--prompts`, one per chunk) so a character can leave frame and return, isolating what only the scratchpad could carry; run it with and without `--no_condition_on_last_frame` and compare. Launcher: [Wan2.2-TI2V-5B-memory-test-eval.sh](examples/wanvideo/model_inference/memory-test/Wan2.2-TI2V-5B-memory-test-eval.sh), whose `INNER_FLAGS` must mirror the checkpoint (`--optimizer`, `--num_gradient_steps`, `--lora_rank`, `--num_anchor_latent_frames`).
- **Subclassing the generator** — `WanE2ETTTSequentialGenerator` exposes exactly two extension points, `_chunk_prompts` (per-chunk prompt schedule; base broadcasts one prompt) and `_log_prefix`. **Do not override `generate`.** The memory-test driver used to, with a copied chunk loop that then silently rotted: the copy predated the wide anchor, so it passed no `anchor_frames`, never refreshed a `cond_frames` window, and hardcoded `num_pinned_pixel_frames(2 if sink_active else 1)` — running a k=3 φ₀ through it conditioned on a 1-latent anchor and trimmed 5 boundary frames instead of 13, measuring something the checkpoint was never meta-trained for. The loop owns the anchor handoff, the sink, the k>1 block, boundary trimming and the per-video `TestTimeInnerOptimizer`; all of that must stay in one place.
- **Inner-loop diagnostics (`--ttt_diagnostics`)** — `TTTDiagnostics` in [e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py) traces what the test-time inner loop is doing per chunk, for "quality keeps degrading as the chunk count grows". Wired into [custom-prompts/Wan2.2-TI2V-5B-e2e-ttt-custom.py](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-e2e-ttt-custom.py) only (`--ttt_diagnostics PATH`, `--ttt_probe_seeds`); off by default, and every hook is a single `is not None` check. Read the JSONL with [eval/ttt_diagnostics/summarize.py](eval/ttt_diagnostics/summarize.py) (table is stdlib; `--plot` needs matplotlib, which on this box is only in the `data` env).
  - **The per-chunk `loss=` print cannot be read as a trend.** `compute_flow_matching_loss` draws ONE random timestep per MC sample and the inference configs set `num_mc_samples: 1`; flow-matching loss varies by >1 order of magnitude across σ, so that line is a single random-σ draw and the noise swamps 23 chunks of signal. Everything compared across chunks therefore comes from a **fixed probe** — `torch.random.fork_rng` + a fixed seed pins both timestep and noise. `fork_rng` also means the sampling stream is untouched, so clips stay byte-identical with the flag on and chunk seeds keep matching the no-adaptation ablation.
  - Two probes: `probe_self` (current φ vs the chunk just generated, taken *before* its memorize step, so it reads as the generalization the meta-objective buys, not fit quality) and `probe_chunk0` (current φ vs **chunk 0's latents held fixed for the whole video** — nothing varies but φ, so a rise is unambiguous forgetting of the video's start).
  - Magnitudes per optimizer step: grad norm pre/post `_per_tensor_clip`, the displacement actually realized (measured on the fp32 master before vs after `opt.step`), cumulative `‖φ−φ₀‖` **split lora_A/lora_B** (B is zero-init, so whatever meta-training left there is the whole denominator and B's relative drift is the one that can pass 1 while the aggregate looks tame), and `precond_gain = step_norm/(lr·‖g‖)` — AdamW moves each coordinate by ~lr *however small the gradient got*, so a flat loss with a climbing gain means the optimizer is walking at full speed on noise. Per chunk: `delta_w_ratio = ‖scaling·B@A‖/‖W_base‖`, the only gauge-invariant magnitude (A/B norms individually are invariant to `A→cA, B→B/c`). `live_over_master` is drift as the bf16 DiT sees it over drift as the fp32 master holds it — measured at 0.85 on a toy, i.e. the write-back still discards ~15%, the residue of the bug that made the pre-master in-place bf16 `sub_` discard nearly all of it.
  - **The depth arithmetic this exists to test.** The k3 arms run `num_chunks 24 × ttt_steps_per_chunk 1 × num_gradient_steps 2` = **46 AdamW steps monotonic from φ₀ with no reset inside a video** (`generate` restores φ₀ only *between* narratives). Meta-training at `fpc=53`/stride 40 over 160–960-frame clips gives 3–23 chunks → `2·(chunks−1)` = 4–44 steps, median ~10–12, and only 1.7% of clips exceed 20 chunks. So the last third of every generated video runs the scratchpad deeper than ~98% of meta-training ever went, and AdamW is why it does not self-limit.
- **No-adaptation baselines** (same chunk loop, base weights, no LoRA and no TTT — the arms an E2E-TTT number is read against): [custom-prompts/Wan2.2-TI2V-5B-chunk-by-chunk-custom.py](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-chunk-by-chunk-custom.py) is the plain one (single last frame via `input_image`, `--no_condition_on_last_chunk` for independent chunks), and [custom-prompts/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-custom.py](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-custom.py) reproduces the **full E2E-TTT anchoring** — wide k-frame block (`--num_anchor_latent_frames`, default **3** here, vs `1` on the TTT scripts) plus the first-frame sink, same `--no_*` flags and same sink normalization — so the LoRA scratchpad is the only difference from a TTT run. It imports `anchor_overlap_pixel_frames` / `num_clean_latents` / `num_pinned_pixel_frames` from [e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py) rather than duplicating the arithmetic, and raises upfront if `--frames_per_chunk` is too short for the anchor window. Commented invocations for both live in [Wan2.2-TI2V-5B-custom-prompt-eval.sh](examples/wanvideo/model_inference/custom-prompts/Wan2.2-TI2V-5B-custom-prompt-eval.sh), which by convention keeps exactly one line uncommented per run. Both have VBench-suite drivers under [vbench/](examples/wanvideo/model_inference/vbench/) with the same `--config` / sharding / `<prompt>-<index>.mp4` protocol as the TTT one: [vbench/Wan2.2-TI2V-5B-chunk-by-chunk-vbench.py](examples/wanvideo/model_inference/vbench/Wan2.2-TI2V-5B-chunk-by-chunk-vbench.py) (plain) and [vbench/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.py](examples/wanvideo/model_inference/vbench/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.py) (full anchoring; config [Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.yaml](examples/wanvideo/model_inference/configs/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.yaml) mirrors the k3-720p TTT arm's geometry at `fpc=49` / 24 chunks so total length matches — VBench metrics are length-sensitive, so keep `num_chunks`/`frames_per_chunk`/k/resolution equal across arms). All three drivers derive chunk seeds identically (`base_seed + index*num_chunks + k`), so arms share seeds clip for clip.
- **VBench submission: one shape for all four arms** — every arm under [vbench/](examples/wanvideo/model_inference/vbench/) is now a three-layer stack with an identical interface: `<arm>-vbench.py` (the driver) ← `<arm>-vbench.sh` (takes `[dimension] [num_videos_per_prompt]`, validates the dimension against `$VBENCH_ROOT/prompts/prompts_per_dimension/` *before* loading ~10 GB of weights, reads `CONFIG`/`SAVE_PATH`/`VBENCH_ROOT`/`LORA` from the environment, and prints the `vbench evaluate` lines its clips unlock) ← `<arm>-vbench.sbatch` (one dimension per GPU, forwards `"$@"`). - **Three anchoring routes, one per conditioning mechanism.** How a chunk is anchored on its predecessor is a property of the *DiT*, not a free choice, so `train_e2e_ttt.py` picks a route from the loaded model's flags (`self.anchor_route`) instead of asking. **φ₀ checkpoints are not interchangeable across routes.**
  - `fused` — `fuse_vae_embedding_in_latents` (**Wan2.2-TI2V-5B only**). Clean latents overwrite the chunk's own leading latents and are marked clean by a per-frame timestep. The original route; everything under "Wide local anchor (`k`)" below describes it.
  - `i2v` — `has_image_input and require_vae_embedding` (**Wan2.1-Fun-\*-InP, Wan2.1-I2V-\***). Uses the checkpoint's *pretrained* I2V conditioning: `y` = 4 mask channels + 16 image-latent channels on the channel axis (`in_dim` 36), plus CLIP tokens prepended to the cross-attention context. See the dedicated bullet below.
  - `none` — plain T2V (`Wan2.1-T2V-1.3B/14B`). No image-conditioning mechanism exists, so the LoRA scratchpad is the only channel across a boundary. An experimental fourth mechanism for this case, the **attention prefix anchor** (`anchor_latents` on `model_fn_wan_video` + `attention_anchor_latents` in [e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py)), prepends clean latents as extra token positions at timestep 0 using the per-token modulation path `DiTBlock` already has — no new parameters, no pinned frames, no boundary trim. Unlike the other two its conditioning is untrained at init, so φ₀ would have to learn the mechanism as well as the scratchpad. **It is not reachable from `examples/`.** The library side is complete — `InferenceConfig.attention_anchor`, `attention_anchor_latents`, the `attention_anchor=` parameter of `run_meta_inner_loop`, `anchor_latents=` on `compute_flow_matching_loss` / `model_fn_wan_video`, the `attn_anchor` branch of `WanE2ETTTSequentialGenerator.generate`, and `ErrorRecycler.harvest(attention_anchor=…)` — but **nothing selects it on either side**: [train_e2e_ttt.py](examples/wanvideo/model_training/train_e2e_ttt.py) has no `--e2e_attention_anchor` flag and never passes `attention_anchor=` at its single `run_meta_inner_loop` call site, and no inference driver sets `InferenceConfig.attention_anchor`. (A dead `e2e_attention_anchor` kwarg sat unused on the training module's `__init__` until it was removed, so this route has never actually been meta-trained.) Turning it on means adding a flag at *both* entrypoints, not just writing a config. **Positional caveat for whoever does:** the prefix is patch-embedded and prepended, then `f += num_anchor_frames` and the RoPE grid is rebuilt over the concatenated `f` ([wan_video.py:1700](diffsynth/pipelines/wan_video.py#L1700)) — so anchor tokens get local indices `0..n−1` and the chunk shifts to `n..`, exactly matching the fused route's layout, and *never* an absolute frame number. That is the safe design and it should stay that way: Wan's `dit.freqs[0][:f]` ([wan_video_dit.py:533](diffsynth/models/wan_video_dit.py#L533)) is always local, TI2V-5B only ever saw frame indices ~0–30 (121 frames → 31 latents), and a 24-chunk video would need ~244 — 8× extrapolation, in-table (`end=1024`) but untrained. If long-range retrieval is ever added and memory tokens *do* carry global indices, RoPE periodicity then lets a distant memory frame phase-align with a prediction frame and get copied wholesale; the fix is Matrix-Game 3.0's head-wise perturbation `θ̂_h = θ_base(1 + σ_θ ε_h)`, `σ_θ = 0.8` ([arXiv:2604.08995](https://arxiv.org/abs/2604.08995)). Until then it is a no-op here — our index span is 0..13 in both routes and aliasing cannot occur.
- **The `i2v` route (SVI-style) — `--e2e_num_motion_frames` / `--e2e_ref_pad_num` / `--e2e_p_motion_threshold`.** Ported from [Stable-Video-Infinity](https://github.com/vita-epfl/Stable-Video-Infinity) (`diffsynth/pipelines/svi_video.py::encode_images_adaptive`), which drives `Wan2.1-I2V-14B-480P` — the 14B sibling of `Wan2.1-Fun-V1.1-1.3B-InP` — exactly this way with LoRA-only tuning. `y` is built as `vae_input = [m motion pixel frames] ++ [ref-frame or zero padding]`, encoded untiled, with the mask packed 4 channels per latent frame. Three things are load-bearing:
  - **The mask is never widened.** It stays at the pretrained `[1, 0, 0, …]` pattern — only pixel frame 0 marked *given* — for every `m`. SVI has a `ref_pad_cfg` switch that would widen it and **no shipped script enables it** (`gradio_demo.py` passes it explicitly `False`). All the extra conditioning rides in the image-latent **content**, in regions the mask calls "not given": context the model may use, not frames it is told to reproduce. That is what keeps the conditioning channel in-distribution, and it is why `m` costs nothing in mask-distribution terms. Verified bit-exact against SVI across `m ∈ {1,5,9} × ref_pad_num ∈ {0,-1,3}`.
  - **`m` is in PIXEL frames**, unlike the fused route's latent-frame `k`. The causal VAE turns `m` into `motion_latent_frames(m) = (m-1)//4+1` latents of real content: 1→1, **5→2**, 9→3. SVI-Shot/Talk/Dance use `m=1, ref_pad_num=-1`; SVI-Film `m=5, ref_pad_num=0`; **SVI 2.0 `m=5, ref_pad_num=-1`** — wide window *and* full reference padding, which the configs here start from. `m` is also the chunk overlap, so each chunk contributes `frames_per_chunk − m` new frames.
  - **The "sink" is `ref_pad_num`, not a pinned latent.** Rather than zeros, the non-motion slots of `y` are filled with a fixed reference frame (`-1` = every slot, SVI's "padding for ID consistency"; `n>0` = the first n). *Which* frame is `--e2e_ref_frame_source`, and it defaults to **`first`**, not SVI's `random`. Inference has always used the video's own first frame — `WanE2ETTTSequentialGenerator` captures `frames[0]` after chunk 0 and hands the same one to every later chunk (`--input_image`, when given, seeds that same frame), so a random training reference was the one train/test gap left on this route. It also biased the wrong way: a random frame is on average more contemporaneous with the chunk being predicted than frame 0 is, and is a *future* frame about half the time, so φ₀ was meta-learned under a strictly more informative reference than it gets at test time. SVI draws randomly because *its* reference is a user-supplied still that need not belong to the video at all — robustness we don't need. `random` remains available to reproduce SVI, and φ₀ is not interchangeable across the two. The fused route already used the first frame on both sides (`sink_frame = chunks[0][:, :, 0:1]`), and its `--e2e_condition_on_sink_frame` does **not** apply here and is forced off.
  - Other details: the loss is **unmasked** (nothing is pinned, so the leading frames are still noised and still supervised — the model reconstructs them *from* `y`, as in I2V pretraining); the anchor's cost is paid in new content per chunk, trimmed by `drop_boundary_frame` (SVI trims the previous chunk's *tail* instead — same count, but head-trimming keeps the original frames rather than a regeneration). Chunk 0 needs no special case: it passes the start image repeated `m` times, a regime meta-training *can* mix in via `p_motion_threshold` — but the CLI default of `0.9` is **not** what the shipped config uses. It sets `1.0` (always a real motion window), because we sample without `--input_image`, so chunk 0 gets the null conditioning rather than a repeated still, and because the draw can only ever land on chunks 1..n−1 (chunk 0 is never a predict target), pairing a still window with an already-adapted φ_K when inference needs φ_0. Restore `0.9` if this arm ever samples with `--input_image`. CLIP encodes the window's **first** frame. `(y, clip_feature)` depend only on pixels, so they are built **once per chunk** in `_encode_chunks` and passed in detached, keeping the VAE and CLIP towers off the meta-graph. The memorize objective stays unconditioned in *content*, but a `require_vae_embedding` DiT cannot forward without a `y` at all, so it is given the **null conditioning** (zero mask, zero latents) — and `ttt_update_inplace` must be handed the same tensor or the test-time update is a different rule from the meta-trained one. Error recycling injects only into `y[:, 4:, :n_motion]` (never the mask channels, never the non-drifting reference padding). Config: [Wan2.1-Fun-V1.1-1.3B-InP-e2e-ttt-fomaml.yaml](examples/wanvideo/model_training/configs/Wan2.1-Fun-V1.1-1.3B-InP-e2e-ttt-fomaml.yaml) at 480×832 — the only one left, the maml/reptile siblings having been deleted in `32f9aee0` (their launchers still default to those paths). It **must** list the CLIP weights in `model_paths`, or `pipe.image_encoder` is `None`, no chunk ever gets image tokens, and the whole i2v conditioning channel degrades to `y` alone. **Custom-prompt eval — the same four-arm shape as TI2V-5B**, under [custom-prompts/](examples/wanvideo/model_inference/custom-prompts/): [`-base-`](examples/wanvideo/model_inference/custom-prompts/Wan2.1-Fun-V1.1-1.3B-InP-base-custom.py) (single pass), [`-chunk-by-chunk-`](examples/wanvideo/model_inference/custom-prompts/Wan2.1-Fun-V1.1-1.3B-InP-chunk-by-chunk-custom.py) (stock single-frame I2V continuity, i.e. the motion-unidentifiable anchor), [`-chunk-by-chunk-anchored-`](examples/wanvideo/model_inference/custom-prompts/Wan2.1-Fun-V1.1-1.3B-InP-chunk-by-chunk-anchored-custom.py) (full i2v anchoring, no LoRA) and [`-e2e-ttt-`](examples/wanvideo/model_inference/custom-prompts/Wan2.1-Fun-V1.1-1.3B-InP-e2e-ttt-custom.py), all sharing one [`-custom-prompt-eval.sh`](examples/wanvideo/model_inference/custom-prompts/Wan2.1-Fun-V1.1-1.3B-InP-custom-prompt-eval.sh)/`.sbatch` (one uncommented line per run) and the same `--prompt`/`--prompt_file` + one-pipeline-load + `--skip_existing` protocol. `--input_image` on all four is `nargs="+"`: **one** image shared by every prompt, or **exactly one per prompt** — SVI's `(frame.jpg, prompt.txt)` pairing — and any other count raises rather than silently handing some prompt the wrong reference frame. A second launcher, [`-svi-shot-eval.sh`](examples/wanvideo/model_inference/custom-prompts/Wan2.1-Fun-V1.1-1.3B-InP-svi-shot-eval.sh) `<arm> [num_chunks]` + its `.sbatch` (which forwards `"$@"`), runs the four arms on SVI's own [`data/toy_test/shot`](https://github.com/vita-epfl/Stable-Video-Infinity/tree/main/data/toy_test/shot) example with `--input_image` — the regime SVI actually ships, where no chunk is ever unconditioned. It takes the arm as an **argument** rather than by commenting lines, because the `.sbatch` reads the `.sh` at job start, so two commented-line submissions would race; that is also why a new arm goes in its `case`, not in a new file. Geometry is `fpc=45` / `m=5` → **stride 40**, deliberately equal to the 5B k3 arms' stride, so a fixed chunk count gives the same video length in both families (24 chunks → 965 frames, which is the base arm's `--num_frames`). The anchored arm's chunk loop is a mirror of the generator's i2v branch rather than a fork of it — verified equivalent (identical per-chunk `anchor_frames`/`ref_pad_num`/`sink_image` and identical emitted frames) across `m ∈ {1,5,9}`, `ref_pad_num ∈ {-1,0,3}`, seeded and unseeded, and both `--no_*` flags. Two things to know when sampling without `--input_image` (the default): chunk 0 gets the **null conditioning** — no motion window, so no CLIP tokens from a real frame — and chunk 0 is never a predict target in meta-training, so its regime is meta-trained only as a memorize input. **The null-CLIP case is not a no-op and used to corrupt the text conditioning outright.** `CrossAttention.forward` splits `context[:, :257]` off as image tokens whenever the DiT was built `has_image_input` ([wan_video_dit.py:187](diffsynth/models/wan_video_dit.py#L187)) — the slice is baked in at construction, not conditional on what `model_fn_wan_video` passes. So skipping the CLIP prefix on a `clip_feature=None` call did not "run without image tokens": it fed the first 257 **text** tokens through `k_img`/`v_img` and left the text branch reading `context[:, 257:]`, which umt5 zero-pads for any prompt under 257 tokens — i.e. the prompt was dropped entirely and chunk 0 denoised into promptless texture. `model_fn_wan_video` now substitutes the null CLIP descriptor (`zeros(B, 257, 1280)`, the same condition-drop encoding [WanVideoUnit_FunControl](diffsynth/pipelines/wan_video.py#L742) uses) so the prefix is always present and only its *content* says "no image". This hit **every memorize / `ttt_update_inplace` step** too, since the null conditioning carries no `clip_feature` by construction — symmetric across train and test, so not a train/test gap, but the inner loss was being fit against a forward with no text conditioning, and a φ₀ meta-trained before this fix is not consistent with the corrected inner update. Fused-route models (TI2V-5B, `has_image_input=False`) are unaffected; in this registry `has_image_input` and `require_clip_embedding` are always true together, so the guard is exact. These configs use **SVI-Film's** error-recycling probabilities, which are now also the CLI defaults and what every `Wan2.2-TI2V-5B-*` config sets — see the recycled-error bullet below.
- **Wide local anchor (`k`)** — *fused route only.* `--e2e_num_anchor_latent_frames` (training) / `--num_anchor_latent_frames` (inference), default `1`. A *single* anchor latent is motion-unidentifiable — no velocity can be read off one frame — so at k=1 the only channel carrying motion **direction** across a chunk boundary is the LoRA scratchpad, whose memorize objective is unconditioned flow matching and therefore dominated by appearance. That is the known cause of next chunks that reverse the preceding motion. k>1 pins a contiguous *block* of the previous chunk's tail, putting velocity directly in the conditioning. The two values must match between the φ₀ checkpoint and the sampling script — k sets both how many leading latents are pinned and how many decoded frames each chunk hands forward. Mechanics: `anchor_overlap_pixel_frames(k, sink)` is both the meta-training chunk overlap and the inference handoff window, so anchor latents are byte-identical across train/test; with a sink the block is displaced to latent positions `1..k` (sliced as `x0[:, :, 1:1+k]`) and the window carries one extra leading frame purely as VAE causal context, whose latent the sink overwrites — hence `4k+1` (k=3 → 13 pixel frames of overlap, 12 anchored). The anchor block **must** come from one contiguous VAE encode: Wan's causal VAE gives latent 0 one pixel frame and later latents four, so stacking standalone single-frame encodes at positions >0 yields wrong statistics (`WanVideoUnit_ImageEmbedderFused` takes an `anchor_frames` list and encodes it in one pass). It must also be an **untiled** encode, matching `_encode_chunks`'s `tiled=False`: tiled encoding splits the frame spatially and alpha-blends overlapping tiles, which does not reproduce the whole-frame encode. `WanVideoUnit_ImageEmbedderFused` therefore pins `tiled=False` on all three of its encodes (anchor window, sink, single `input_image`) and ignores the caller's `tiled`, which now governs only the output *decode* — that has no training-side counterpart, and untiled decode of a full chunk would be a real memory regression. This was resolution-dependent and so easy to miss: with `WanVideoVAE38` (`upsampling_factor=16`) the pipeline default `tile_size=(30, 52)` latents covers 480×832 in exactly **1** tile (verified: blend mask strictly positive, so identical to untiled), but 704×1280 splits into **6** — meaning every 720p arm sampled before this fix conditioned on tile-blended anchor latents that meta-training never produced, while the 480p arms are unaffected. The recycled anchor y-error is likewise harvested and injected as one coherent k-frame block (the predict chunk's last k latents) — independent per-frame draws would inject temporally incoherent noise into the exact cue k exists to provide. **k=1 is a deliberate legacy special case** (anchor at `x0[:, :, 0:1]`, sink prepended, 1-frame overlap) so pre-existing φ₀ checkpoints still reproduce. Cost: pinned frames are given context, not supervised content — at `frames_per_chunk=41` a k=3+sink block pins 4 of 11 latents (7 supervised vs 9 at k=1), so raise `e2e_frames_per_chunk` rather than accepting a weaker meta signal. Watch `train/num_anchor_latent_frames` and `train/anchor_overlap_frames`. Ready-made pairs, **both now at `fpc=53` on the training and the sampling side** (14 latents, 4 pinned, 10 supervised, overlap 13 → stride 40): [fomaml-k3-720p.yaml](examples/wanvideo/model_training/configs/Wan2.2-TI2V-5B-e2e-ttt-fomaml-k3-720p.yaml) + [k3-720p-vbench.yaml](examples/wanvideo/model_inference/configs/Wan2.2-TI2V-5B-e2e-ttt-k3-720p-vbench.yaml) (720p training, 480p sampling) and [fomaml-k3-480p.yaml](examples/wanvideo/model_training/configs/Wan2.2-TI2V-5B-e2e-ttt-fomaml-k3-480p.yaml) + [k3-480p-vbench.yaml](examples/wanvideo/model_inference/configs/Wan2.2-TI2V-5B-e2e-ttt-k3-480p-vbench.yaml). 53 is the length that restores the k=1 baseline's training **stride** of 40 (its overlap is the legacy 1 frame, so 41−1 = 53−13) while carrying one *more* supervised latent than it, and it makes train and test chunk lengths equal. Both arms and the no-adaptation ablation [chunk-by-chunk-anchored-vbench.yaml](examples/wanvideo/model_inference/configs/Wan2.2-TI2V-5B-chunk-by-chunk-anchored-vbench.yaml) run `fpc=53` / `num_chunks=24` → **973 frames**, so the three are length-matched; the k=1 arm ([e2e-ttt-vbench.yaml](examples/wanvideo/model_inference/configs/Wan2.2-TI2V-5B-e2e-ttt-vbench.yaml)) is also at `fpc=53` but pins only 2 latents (5 pixel frames), so it emits 48/chunk and 1157 total — k sets the per-chunk overhead, so equal fpc *and* equal chunk count cannot also equalise length against k=1. The earlier `fpc=49` pairing (9 supervised, 36 new frames, 877 total) and the 480p `fpc=93` / `num_chunks=11` variant are both retired. Note the k=1 *training* config was deleted in `32f9aee0`; its geometry survives only in that inference config.
- **Frame sampling (`--fix_frame_rate` / `--frame_rate`)** — `--fix_frame_rate` (default **off**) resamples every clip's time axis to `--frame_rate` (default `None`, and **only read when `--fix_frame_rate` is set**); off, clips are read as their native frame sequence and `--frame_rate` is inert. The pair is enforced: `--fix_frame_rate` without an explicit `--frame_rate` raises in [train_e2e_ttt.py](examples/wanvideo/model_training/train_e2e_ttt.py) rather than inheriting a default. Getting the target fps *wrong* is worse than leaving the switch off — resampling **down** just drops frames, but resampling **up** duplicates them, making consecutive outputs identical and the inter-frame motion zero, which poisons exactly the velocity cue a k>1 anchor block exists to carry (16fps clips at `--frame_rate 24` duplicate every third frame). `LoadVideo` warns per clip when the source fps is below the target; such clips should be *filtered out*, not resampled up. The five `Wan2.2-TI2V-5B-*` configs set `fix_frame_rate: true` / `frame_rate: 16`: the clips are already 16fps (resampled offline — `rsfps16` in `output_path`, verified byte-identical: same frames, ≤4 fewer at the tail on some clips), but that uniformity was an **unenforced precondition living only in a preprocessing step**, and E2E-TTT is unusually sensitive to it. It is also strictly cheaper — the frame count then comes from the container's `duration` instead of `reader.count_frames()`, which shells out to a full `ffmpeg -c copy -f null -` demux pass (0.7–2.5 s on a 300-frame 540p clip). [operators.py](diffsynth/core/data/operators.py) was reworked to pay for that pass only when unavoidable: `count_frames()` per clip went 2 → 1 with `fix_frame_rate` off and 2 → **0** with it on, and `LoadVideo` now guards `get_data` with an `IndexError` catch (a `duration` that over-states the real length truncates and re-snaps to the division factor instead of crashing). `map_single_frame_id`'s `total_raw_frames` is now optional for the same reason.
- **Throughput: length-grouped batching + prefetch** — under DDP every rank blocks at the gradient all-reduce, so a step costs as much as its **longest** clip; chunk counts span 3–23 (median 6) on `ultravideo_long_filtered_all_16k`, and a random window of 8 almost always contains an outlier (`Σ_steps max(n)` = 1.92× the balanced floor). `--length_grouped_batching` (opt-in) replaces the default global shuffle with `LengthGroupedSampler` in [train_e2e_ttt.py](examples/wanvideo/model_training/train_e2e_ttt.py), passed through the new `sampler=` parameter of `launch_training_task` ([runner.py](diffsynth/diffusion/runner.py)). It works purely by *reordering* because accelerate shards a `batch_size=1` loader round-robin (`BatchSamplerShard._iter_with_no_split`: sampler position `i` → rank `i % num_processes`) without reordering, so the clips co-resident in one step are exactly the contiguous window `[g·G, (g+1)·G)` where `G = num_processes * gradient_accumulation_steps`. Scheme (HF's "sortish"): global shuffle → cut into megabatches of `G * --length_group_megabatch_mult` → sort each by length → cut into `G`-sized groups → **shuffle the groups**. That last shuffle matters: without it clip length correlates with training *time* and the LR warmup/cosine and the `ErrorRecycler` warmup each see a biased slice. Measured at 8 GPUs: 1.92× → 1.03×, 76% of steps perfectly uniform, ~1.87× predicted speedup. `--length_column` (default `num_frames`, generated by [add_length_column.py](datasets/ultravideo_long/add_length_column.py)) is a **scheduling hint only** — `LoadVideo` still measures the real length, so a stale value costs balance and can never change what is trained. Note `--length_group_megabatch_mult` runs the *opposite* way to its help string: `1` degenerates to a plain random shuffle (the sort window equals one group), and only `≥ len(dataset)/G` approaches a global sort; the default `50` (400-clip window) captures ~98% of the benefit while keeping sampling randomness. The startup `imbalance_report` line models step cost as `max` over the whole window, which is exact at `gradient_accumulation_steps=1` and over-states the speedup above it. Orthogonal second lever: `--dataset_num_workers` defaults to **0**, i.e. video decode (5–11 s/clip) runs synchronously on the training loop's critical path; the TI2V-5B configs set `2`, which drops the measured per-step stall from ~6.5 s to ~1.0 s (the residue is IPC of the decoded PIL frames). Cost is `workers × prefetch_factor(2) ×` clip size (~1.2 MB/frame at 480p, ~2.8 MB at 720p).
- **Two correctness constraints** (both handled in code): (1) second-order grads (`maml` only) require double-backward attention — `enable_double_backward_attention()` disables fused flash/sage kernels and pins math SDPA; it is called only when `--e2e_algorithm maml`, since FOMAML and Reptile each do a single backward per inner step and run fine with fused kernels; (2) the differentiable override path and activation checkpointing used to be **incompatible** — a whole-model `_reparametrize` context restores φ₀ before the backward, and non-reentrant checkpoint recomputes *after* that context exits, so the meta-gradient was taken at the wrong weights. They are now compatible: `_override_checkpointed_blocks` checkpoints each DiT block individually and passes that block's override tensors as **explicit checkpoint inputs**, so φ_k is live in both the recompute and the outer meta-backward. `compute_flow_matching_loss` therefore honours `use_gradient_checkpointing` unconditionally (`gc = use_gradient_checkpointing`, no forcing) on both the memorize and predict paths. **Do not read this as "checkpointing is off during meta-training"** — it is on whenever the config says so, and the 720p memory model (`alloc_GB ≈ 10.8 + 3.56·num_chunks`) is the *checkpointed* number. Turning it off at 720p raises the per-chunk slope by roughly an order of magnitude and OOMs on essentially every clip; see the `use_gradient_checkpointing` note in [fomaml-k3-720p.yaml](examples/wanvideo/model_training/configs/Wan2.2-TI2V-5B-e2e-ttt-fomaml-k3-720p.yaml).

- **Recycled-error injection probabilities — `noise/latent/y/clean = 0.01/0.9/0.9/0.5`,** the CLI defaults ([train_e2e_ttt.py](examples/wanvideo/model_training/train_e2e_ttt.py)) and what every shipped config sets. The near-zero `noise_prob` is the load-bearing one: noise injection is the only mode whose error lands in the **target** (`target = noise_w_error − x0`), so it trains the model to *reproduce* the recycled error instead of correcting for it — every other mode corrupts inputs against a clean target. SVI-Film independently settled on `0.01`, and Matrix-Game 3.0 ([arXiv:2604.08995](https://arxiv.org/abs/2604.08995) — same Wan2.2-TI2V-5B base, same `4 past + 10 noisy` latent geometry as our k=3+sink `fpc=53`) recycles residuals into history and memory latents only, with no noise-injection mode at all. `clean_prob 0.5` keeps half the outer steps uncorrupted so the predict loss retains a clean signal. The earlier `0.9/0.9/0.9/0.1` defaults are not reproducible from the current tree — a φ₀ meta-trained under them saw a materially different inner/outer objective.
- **Recycled-error buffer memory — host RAM is the binding constraint, not GPU.** The `ErrorRecycler` replay buffers are what killed the 720p arms: job 4077159 grew RSS linearly with `err_buffer/total_samples` (3.87 MB/sample, r=0.994) from 18 GB to 75 GB by step 780, then slurm OOM-killed 4 ranks. Two changes cut it, both in [e2e_ttt.py](diffsynth/diffusion/e2e_ttt.py):
  - **One buffer instead of two.** With `d = noise_pred − training_target`, SVI's two one-shot extrapolations are exactly `noise_error = d·(1−σ)` and `y_error = −d·σ` — the same residual at two scales, since `noisy_latents` cancels out of both. `residual_buffer` stores `(d, σ)` pairs and the samplers apply the coefficient on the way out. Verified **bitwise** (max|Δ| = 0), including through the pinned-frame zeroing. Two details make it exact: **σ is stored per sample** (the harvest σ comes from the *training* scheduler and is finer than the grid it is filed under — measured 0.9066 vs 0.9211, so re-deriving it from `_get_timestep_grid` would inject a 1.6% scale error), and `d` is stored raw, since recovering it from a stored `noise_error` divides by `1−σ`, ill-conditioned at the high-σ end `sigma_shift=5.0` favours. The two full-chunk injections now sample **without replacement** within one predict draw (`_last_residual_idx`), so they can never draw the same residual and inject two collinear errors. The anchor buffer stays separate — different population (predict-step, anchored branches only) and different read path (`anchor_sample_from_all_grids`).
  - **One arena per NODE instead of per rank** — `--e2e_shared_buffer_dir` (opt-in; also `E2E_TTT_SHARED_BUFFER_DIR`). `_SharedSlotArray` mmaps a file every local rank maps, cutting host RAM by the local world size *and* raising diversity: each rank now draws from every rank's samples, which is closer to SVI (it `all_gather`s; per-process buffers were our simplification). **No collective communication** — a shared mapping, not synchronised state; nothing crosses the node boundary and NCCL is untouched. Lock-free: disjoint per-rank write partitions plus a per-slot seqlock, and a torn read returns `None`, which this code already treats as an ordinary miss, so there is no retry loop and no lock. Arenas are built lazily on the first harvest (the shape is not known earlier), created once per node via `O_EXCL` election + atomic rename, and any failure latches off with a warning rather than taking training down. Watch the new `err_buffer/shared` to confirm it engaged.
  - **Sizing.** At 720p / `fpc=53` (latent `48×14×44×80` bf16) a residual is 4.73 MB and an anchor slice 1.01 MB, so at `num_grids=50` one unit of `k` costs **0.287 GB/node**. Against `--mem=368G` minus ~115 GB measured non-buffer and a 10% margin ⇒ **216 GB available, k_max ≈ 750**. Practically: today's `k=50` drops 57.4 → 14.4 GB/node, or that same 57.4 GB instead buys **k=200**, or restore the `k=96` the OOM forced down at 27.6 GB. Write rate is unchanged at matched capacity (at k=200 each of 4 ranks still owns 50 slots/grid). But `err_buffer/miss_rate` was **already 0 at k=96**, so capacity past saturation buys diversity, not coverage — take k=200, not 750. Use `shared_arena_bytes()` / `max_shared_k()` to recompute for other geometries. **The directory must be NODE-LOCAL and must NOT be tmpfs:** `/dev/shm` pages are unreclaimable with ~1 GiB swap on a 377 GiB node, and a segment leaked by an OOM-kill (SIGKILL — no cleanup can run) then costs the *next* job pinned RAM invisible to slurm's accounting, whereas a file on scratch leaks disk and its pages are reclaimable page cache.

### E2E-TTT TODO

- [ ] Persist and restore `ErrorRecycler` state (`residual_buffer` / `anchor_error_buffer`, warmup `iteration_count`, and counters) when resumable anti-drift post-training is needed. Current uninterrupted 3k-example runs intentionally start with fresh recycler state. Note `--e2e_shared_buffer_dir` makes this nearly free: the arena is already a file, so pointing it at a path that outlives the job persists the buffers as a side effect — what is still missing is the scalar state (`iteration_count`, harvest/injection counters).
- [ ] Store the replay buffers as int8 plus a per-tensor scale — another 2× on top of the two changes above, and well conditioned given the stored value is a stochastic perturbation the code already rescales by `error_modulate_factor`. Note this is unrelated to the finding that fp8 *weight* quantization perturbs the DiT ~10× more than the whole LoRA scratchpad: that concerns quantizing weights on the gradient path (and `torch._scaled_mm` has no backward, which breaks the memorize step), whereas these buffers hold detached additive errors that never see autograd.

**Open design questions — "the memorize objective stores texture, not dynamics".** Both of the following attack the same root cause as the wide-anchor (`k>1`) work, but on the *inner* loss instead of the conditioning: the memorize objective is unconditioned flow matching on a chunk, so what the LoRA scratchpad actually absorbs is appearance statistics, and motion direction is only weakly represented. Both are cheap; neither has been run. (Rejected alternative, for the record: swapping the memorize loss for a **DMD**-style distribution-matching objective. It is not substitutable — DMD needs the sample to be a differentiable function of the params being updated, whereas the memorized `x0` is a detached leaf (ground truth in training, sampler output at test time), so it would require a differentiable rollout per inner step *inside* the MAML graph; and its `s_real` is the frozen teacher, so it is mode-seeking toward *teacher-plausible* video rather than toward *this chunk* — it carries no per-sample identity signal, which is exactly what the scratchpad exists to hold. Making `s_real` sample-specific degenerates back to the flow-matching residual already in use, plus a learned fake-score net of variance. DMD's real place in this project is offline few-step distillation of the base model, orthogonal to TTT, and/or a Self-Forcing-style rollout loss in the **outer/predict** term where "plausible continuation" is genuinely a distribution-level notion.)

- [ ] **Condition the memorize objective on the anchor.** Today it is deliberately unconditioned: the memorize call at [e2e_ttt.py:1449](diffsynth/diffusion/e2e_ttt.py#L1449) passes neither `condition_on_first_frame` nor `sink_frame`/`num_anchor_latent_frames`, and `ttt_update_inplace` ([e2e_ttt.py:1529](diffsynth/diffusion/e2e_ttt.py#L1529)) has no parameters for them either — so train and test are at least *symmetric* in being unconditioned. Conditioned, "memorize" would mean *continue-from-these-frames* rather than *reproduce this clip*, forcing the scratchpad to encode dynamics; the anchor block is precisely where velocity lives (same argument as `k>1`). Implementation is small because the frames are already in hand on both sides: in meta-training `chunks[k]` is overlap-chunked, so its leading `num_clean_latents(k, sink)` latents *are* the anchor; at inference `x0 = chunk_latents` is the sampler's own output for a follow-up chunk, whose leading latents are the ones the pipeline pinned. Open sub-questions: (a) chunk 0 / the first memorize step has no predecessor, so it stays unconditioned — does the inner objective then change shape between step 0 and later steps in a way the meta-learned LR schedule can absorb? (b) pinned frames are excluded from the loss, so a conditioned memorize step supervises `T' − num_clean` instead of `T'` latents — the same supervised-frame tax that made `fpc=49` the controlled setting for k=3; (c) train and test must be changed together (`ttt_update_inplace` needs the new args threaded through `WanE2ETTTSequentialGenerator`), and a φ₀ trained conditioned is not interchangeable with one trained unconditioned.
- [ ] **Bias the memorize timestep window high.** Low-σ draws are where the loss is texture-fitting; high-σ draws carry layout and motion. Training side is config-only — `--e2e_min_timestep_boundary` / `--e2e_max_timestep_boundary` already exist ([train_e2e_ttt.py:544](examples/wanvideo/model_training/train_e2e_ttt.py#L544)) and feed `InnerLoopConfig.min/max_timestep_boundary`; they are distinct from the non-`e2e_` pair, which bounds the outer/SFT loss. Caveat before running it as a pure config sweep: the **inference** scripts never set these fields (see the `InnerLoopConfig(...)` construction in [vbench/Wan2.2-TI2V-5B-e2e-ttt-vbench.py:316](examples/wanvideo/model_inference/vbench/Wan2.2-TI2V-5B-e2e-ttt-vbench.py#L316)), so test-time TTT would keep sampling `0.0–1.0` and no longer match the meta-trained inner update — a CLI flag has to be added on the sampling side for the arms to be comparable.

**Open design questions — "the scratchpad runs deeper, and on dirtier inputs, than meta-training ever went".** Both come from reading **Matrix-Game 3.0** ([arXiv:2604.08995](https://arxiv.org/abs/2604.08995)), which post-trains the *same* Wan2.2-TI2V-5B base on the *same* latent geometry (`4 past-frame latents + 10 current noisy latents`, i.e. our k=3+sink at `fpc=53`) and independently arrives at our sink latent and our residual-recycling scheme — so where it differs is worth taking seriously. Neither has been run.

- [ ] **Randomize the inner-loop depth during meta-training.** The k3 arms run 46 AdamW steps monotonic from φ₀ per video while meta-training's median clip gives ~10–12 (see the depth arithmetic under `--ttt_diagnostics`), so the last third of every generated video is off-distribution in *φ-space*. Matrix-Game's distillation samples its rollout length `k ∼ Uniform(1,6)` per iteration rather than letting the data dictate it. Our cheap analogue does not need longer clips: with some probability, take j extra memorize-only steps (j drawn up to 40+, reusing the chunks already in hand) before the predict loss, so the meta-objective also supervises deep φ. Sub-questions: (a) the extra steps are pure cost with no predict term — cap j by a compute budget, not by clip length; (b) `MetaLearnedLRSchedule` is indexed by step, so a schedule meta-learned over ~10 steps has no entries for step 40 — decide whether it extrapolates, clamps, or gets extended.
- [ ] **Feed the memorize step self-generated chunks.** Meta-training's memorize input is always a GT chunk; at test time it is the sampler's own output. `ErrorRecycler` approximates that gap with statistical residuals, but never closes it — Matrix-Game closes it directly, with a **cold-start stage (600 steps, GT history) then a self-generated stage (2,400 steps)**, which also shows the cost is a few thousand steps rather than a full retrain. Our version: with some probability replace the memorize chunk with a few-step sample from the current φ. Note this is the one place a differentiable rollout is *not* needed — the memorize `x0` is a detached leaf either way (which is exactly why DMD is not substitutable here, see above), so the sample can be generated under `no_grad`.

## VisionReward evaluation (`eval/visionreward/`)

A second evaluation axis alongside VBench: [VisionReward](https://github.com/THUDM/VisionReward)
asks a CogVLM2-video backbone a 29-question yes/no checklist about a clip (three questions
interpolate the generation prompt), maps answers to ±1 and returns the weighted mean — **one
interpretable scalar per clip**, which makes arm-vs-arm comparison cheap and shows *where* arms
differ via per-question yes-rates. Self-contained: checklist and weights are vendored under
`eval/visionreward/assets/`, no VisionReward checkout needed. Full detail in
[eval/visionreward/README.md](eval/visionreward/README.md).

- **Separate conda env, non-negotiable.** VisionReward-Video loads via `trust_remote_code` and its
  remote code uses legacy tuple `past_key_values` + hand-rolled 4-D masks, removed in transformers
  4.47+; the `diffsynth` env is on 5.9.0, so the model cannot load there. `setup.sh` builds a
  `visionreward` env (transformers 4.42.4, torch 2.4.1) and downloads the 25 GB checkpoint to
  `/work/nlp/hzhao/checkpoints/visionreward/VisionReward-Video`. Sampling runs in `diffsynth`,
  scoring in `visionreward`; the two `.sbatch` files activate the right one each. `setup.sh` drives
  pip as `"$CONDA_PREFIX/bin/python" -m pip` and asserts the active env — a bare `pip` on this box
  resolves to `~/.local/bin/pip` and silently installs into (and downgrades) the user's python3.9
  site-packages.
- **Three-layer stack, same shape as the VBench arms**: `score_videos.py` / `sample-demos.sh` ←
  `*.sbatch` ← one shared fan-out [demos-launcher.sh](eval/visionreward/demos-launcher.sh)
  `<sample|score> [arm …]` over the same four arms (`base`, `chunk-by-chunk`,
  `chunk-by-chunk-anchored`, `e2e-ttt-fomaml`). `NUM_SHARDS` splits each arm's prompt list
  round-robin; `DRY_RUN=1` prints the `sbatch` lines. A new arm is a `case` entry, not a new file.
- **The 100-prompt suite** is [prompts/causal_forcing_demos.txt](eval/visionreward/prompts/causal_forcing_demos.txt),
  from [thu-ml/Causal-Forcing](https://github.com/thu-ml/Causal-Forcing/blob/main/prompts/demos.txt) —
  long two-beat narratives ("First she … Then she …"), a better long-video-drift probe than VBench's
  short prompts. At up to 775 characters they **cannot be filenames**, so the VBench
  `<prompt>-<index>.mp4` protocol does not apply; sampling uses the `custom-prompts/*` drivers'
  `<prompt[:30]>/<name>.mp4` layout and `score_videos.py --layout custom` recovers the full prompt by
  matching that prefix against the prompt file (it errors on prefix collisions rather than
  mis-assigning). `--layout vbench` still handles anything under `model_inference/vbench/`.
- **Frame sampling is the one setting that silently changes conclusions.** Upstream's `chat` strategy
  takes the frame nearest each whole second and stops at 24, so on a 60 s clip it scores **only the
  first 24 seconds** — exactly the window before long-video drift appears. `score_videos.py` keeps
  `chat` as default for comparability with published numbers and warns how many clips it truncated;
  `score-demos.sh` overrides to `uniform` (24 frames spread over the whole clip). The two are not
  comparable — keep it fixed across arms. 24 frames is not freely raisable: 66 tokens each against a
  2048-token window.
- **Upstream `inference-video.py` is a demo with a result-invalidating bug**: it compares the decoded
  token to lowercase `'yes'` while the model emits `'Yes'`, so every answer scored −1 and every video
  got the same constant `mean(-weight)`. `visionreward_video.py` fixes that plus decode-once-per-clip
  (was 29 mp4 decodes), encode-once-per-clip (the 63-layer EVA2-CLIP tower ran 29× on identical
  pixels — the biggest speedup), and one decoding step instead of `max_new_tokens=2048`. Measured
  15.5 s/clip at `--batch_size 1`, 10.6 s/clip at 8. `pytorchvideo` is deliberately *not* a
  dependency (unmaintained, fails against modern torchvision) — `install_video_transform_shims()`
  reimplements the one transform the remote code imports.
- **`--verify_batching` is not optional decoration.** `encode_images` returns
  `(frames, tokens_per_frame, d)`, not batch-major; the padded-batch path first shipped with `expand`
  where `repeat` was needed, and the guard caught it. `score-demos.sh` passes it on every job.
- Merge and compare with [aggregate.py](eval/visionreward/aggregate.py), which reports per-arm
  mean ± sem, a **paired** per-prompt comparison against the first arm (removing the
  prompt-difficulty variance that dominates a 100-clip mean), and `--per_question` yes-rates.
